# Anomaly²: Corona Road — Design System

A surveillance-horror game UI built on a unified token system inspired by **Google Material Design 3**: an opinionated palette, type scale, spacing scale, elevation, and motion. Horror atmosphere is layered _on top of_ Material-style hierarchy and consistency, not against it.

The goal is that **any new screen or component can be assembled out of these tokens without inventing new colors, spacings, or fonts.** If something doesn't fit, the token system is what we extend — not the component.

---

## 1. Design Principles

1. **Hierarchy before atmosphere.** Time, strikes, and the report action are the player's anchors; horror flourishes (scanlines, vignette, flicker) layer on top, never compete.
2. **One color per intent.** Green = system OK / start / correct. Amber = caution / cameras with activity. Red = strike / terminate / wrong. Cyan = informational / inert. Surreal violet is reserved for late-phase meta-anomalies.
3. **State is visible.** Every interactive surface has resting, hover, pressed, focused, and disabled states drawn from a 5-step state-layer opacity scale.
4. **Motion is meaningful.** 120 ms for ack (button press), 240 ms for transitions (camera switch, panel reveal), 600 ms for atmospheric pulses (anomaly flash). No motion outside this scale.
5. **Mobile-first, desktop-equal.** Touch swipes, mouse drags, on-screen arrows, and keyboard arrows all switch cameras. The game never assumes a touchscreen.

### 2.3 Category palette

Anomaly categories are shown as **text labels** (CAMERA, OBJECT, ENVIRONMENT, PERSON, SURREAL), never by color or icon alone, and never with emoji (kako-jun, 2026-10-30). The in-game cabinet UI (§8, §11) uses the cream/amber/green/red hardware palette scoped to `.retro` in `src/styles/retro.css`; the old per-category colors are no longer used there.

### 2.4 State-layer opacities

Apply on top of base color (rgba with the base color's RGB).

| Focus    | 0.12                         |
| Pressed  | 0.16                         |

## 3. Typography

A single font stack. Game UI is monospace for the surveillance-terminal feel; titles use the same stack to keep visual unity.

```
--font-mono: 'JetBrains Mono', ui-monospace, SFMono-Regular, Menlo, Consolas, monospace;
--font-sans: Inter, system-ui, sans-serif;  /* reserved for long-form copy only */
```

## 6. Motion

Two easings (in/standard + emphasized-out) and four durations.

```
--ease:      cubic-bezier(0.2, 0, 0, 1);   /* Material standard ease (in & out) */
--ease-out:  cubic-bezier(0, 0, 0.2, 1);   /* emphasized decelerate (toast/flash) */
--dur-fast:  120ms;   /* press / state change                    */
--dur-base:  240ms;   /* transitions, panel reveal               */
--dur-slow:  600ms;   /* atmospheric pulses, anomaly flash       */
--dur-toast: 1500ms;  /* toast auto-dismiss, end-of-game delay   */
```

| Pattern               | Duration | Ease                      |
| --------------------- | -------- | ------------------------- |
| Button press          | 120 ms   | `--ease`                  |
| Camera switch (fade)  | 240 ms   | `--ease`                  |
| Report panel slide-up | 240 ms   | `--ease`                  |
| Screen change (fade)  | 400 ms   | linear (200 out + 200 in) |
| Feedback flash        | 600 ms   | `cubic-bezier(0,0,0.2,1)` |
| Anomaly alert pulse   | 1200 ms  | linear, infinite          |

## 7. Layout

The in-game screen is a single cabinet (`.cabinet` in `src/styles/retro.css`): the CRT monitor on top and the control panel below on phones (tube first, panel under it, full-bleed up to 440 px and at most 560 px wide); at ≥ 900 px the cabinet fills the viewport with the 3:4 monitor on the left and the control panel on the right (panel scaled up with `zoom` from 1200 px). Image preload (#284): `index.html` preloads the cabinet images with `link[data-cabinet-image]`, `src/utils/uiPreload.ts` decodes them and the Caveat font, and the start key waits for that for at most 5 s (the timer is cleared when preload finishes first) before the shift starts. Camera photos (#396): `preloadCameraImages` (`uiPreload.ts`, `createCameraPreloader` in `preload.ts`) downloads and decodes the base photo of all eight cameras (about 3MB) on idle time once the cabinet parts and fonts are ready, low priority (`fetchPriority=low`), each URL once, a failed image ignored (the camera loads it as usual on switching), the images held in `cameraImageCache`; START does not wait for it. It is a budget of its own, outside the 800KB UI budget of `uiAssets.test.ts`. The same URLs the `<img>` uses, so the HTTP cache (and the PWA runtime cache, #388) serves the later request. Overlays are still preloaded on idle once play starts (`preload.ts`); ending-bar.webp (540KB) is not preloaded. On portrait the `.tube` width constants in `retro.css` (`(100dvh - 369px - var(--plate-h))` / `- 296px - var(--plate-h)`, times the frame picture ratio 1246/1679) are the measured height of everything except the picture: constant = base 380 / 307 (44px HUD windows, knob gap 0) plus the fixed terms listed right below and, as a separate variable term, the bottom strip `- var(--plate-h)` (#311, see §10; 20px on portrait), applied to both constants and pinned by `retro.test.ts` (a later PR that changes another height adds its own row to the list and the test). The cabinet has `min-height: 100dvh` so no band is left under it. The page never scrolls past the bottom (#333): every full-screen height (`body` / `#root`, `.retro`, `.cabinet`, `--tube-h`) uses `var(--vh)` (`index.css`: `100vh` as the fallback, then `100dvh` under `@supports`; a vh unit appears only as a fallback right before its dvh), because on a phone `100vh` is the large viewport (address bar hidden), taller than the visible screen, which let the player scroll into a black strip; `src/styles/vh.test.ts` pins this. A browser without dvh (iOS 15.3 and older) keeps the old behaviour (the strip stays, no worse than before). A headless Chromium has no sliding address bar, so `npm run check:scroll` measures the scrollable amount on the title, the note (three story stages), the monitor and the SELECT CATEGORY dialog at six sizes and again after rewriting every `100vh` in the page's CSS to `100vh + 80px` (a stand-in for the large viewport; other vh spellings such as `60vh` are not caught). By hand on a real phone: no strip on swiping down (iOS Safari, Android Chrome), and at 900 px and up (iPad landscape, a landscape phone) the monitor picture (`--tube-h`) must not resize / jump while the address bar slides. The result screen and the screen before a shift are the same paper, the detective's investigation note (#297; `src/components/InvestigationNote.tsx` + `investigationNote.css`, built from the save by `src/utils/investigationNote.ts`, wording in `src/data/investigationNotes.ts`, the only place for it). The paper is drawn at a fixed 340 x 620 and scaled to fit the window (contain, 12 px margin), so it never scrolls and the type stays in proportion (smallest text measured 12.2 px at 360 x 640). Layout top to bottom: title and night number, stamps, four sketch frames (1st to 3rd old person, the child; a frame stays a dashed "?" until its flag is raised; a frame filled in the last shift carries a red "found" mark), the synopsis on CSS ruled lines (7 lines at most; every line one colour) and, on the same ruled sheet directly under its last line, the detective's blue scribbles (each line turned as one piece by its own small angle, the glyphs leaning with it, about its own middle; never detached below a gap; the gap is one rule pitch, 22 px, so each line sits about 5 px above its rule and the rules do not run through the letters: at both ends of every line the base stays 3 px below to 13 px above its rule, held by `npm run check:note-wrap`), and, only on a result that earned them (#325, `src/utils/memoSelect.ts`), up to two more handwritten lines at the end of the synopsis (a hypothesis line from `MEMO_FLAG_TEXT`, then an anomaly's one-liner from the ledger's `memo`; chosen once when the shift ends and kept in `lastShift`, one of each kind per result, carried over when not shown, never shown twice; a hypothesis waits for its `knownFrom` stage; the wording was confirmed by kako-jun (2026-11-12, #325/#344); `npm run check:note-wrap` renders the real result with both lines at every stage, size and language), a two-column form (last night or tonight / all nights, blanks on the first night) with the Shift row under both columns and, at the bottom right, one handwritten action (see below). The Shift row is the in-game clock, not real time: "Until 06:00" for a night that ran out (dawn, true ending), "Withdrew at 01:20" for a withdraw (`msToGameTime` of the saved real ms; the save keeps the real milliseconds). Before a shift (title -> START SHIFT -> note -> the handwritten "Start the shift" / 「勤務を始める」) the stamp is BACKGROUND on the first night and SO FAR afterwards and the synopsis is the story so far: a table per stage (`start` = never played, `none` = played but no frame filled, `elder1` / `elder2` / `elder3` / `child` = the furthest raised flag; `STAGE_ORDER` in `investigationNotes.ts`). No `backdrop-filter` support: no patch. Slow device (`utils/titlePerf.ts`, pure `stepPerf`): `StartScreen` watches the animation frames; when their average interval stays over 50 ms for a 2 s stretch the screen gets `start-perf-lite` (the patch stops, still and faint, like reduced motion, and the photo's drift stops too: a drifting photo under the patch is blurred again every frame; measured at 4x throttling in lite: 16.7 / 16.8 ms / 0% at 1280x720 and 3440x1440, against 33.9 / 50 ms / 22% for the full effect at 1280x720), and after another such stretch `start-perf-off` (no patch, no noise; the photo stays still); it never steps back up (no flicker), and a gap over 1 s between frames (a hidden tab) is not counted. `check:title` item 10 measures that the patch is over the photo, masked, takes no pointer and has a fixed radius of at most 10px, that over the joint cycle the signboard's centre is under the strong part of the patch (mask x opacity > 0.5) for at most 40% of the time, that with the patch centred on the sign at full strength the sign keeps at least half of its edge contrast (it stays legible: the 8px patch keeps 68-77%) while the middle of the patch (central 40% x 40%) changes the picture by at least a floor that falls with the screen width because the wide crop is plain wall (about 0.8x of the measured 8px value at each size: 7.5 / 5.0 / 4.5 / 2.8 / 2.0 / 1.5 / 1.1 grey levels under 500 / 700 / 1000 / 1600 / 2200 / 3000 / wider px); the floors sit between the 4px patch kako-jun could not tell from none (measured 5.7 / 2.1 / 1.5 / 0.8 at 360 / 1280 / 1920 / 3440 px wide; `check:title` fails with `--blur-px: 4px`, tried once) and the 8px one (9.4 / 3.6 / 2.5 / 1.5), and that with reduced motion nothing animates. The 8px limit is by measurement on Chromium (swiftshader): the sign stays legible even at 20px, and no tiling artefact appears up to 12px (an earlier \"grid\" at 7 and 10px was the title noise burst in the screenshot, not the blur); 10px is kept as the ceiling in `check:title` and the CSS test. Performance (Chromium with swiftshader software rendering, CPU throttled by CDP, 12 s windows of rAF intervals; frame interval mean / 95th percentile / share over 33 ms): at 360x640 the blur alone costs nothing measurable up to 4x throttling (16.7 / 16.7 ms / 0%), blur plus the noise bursts 21 / 50 ms at 4x and 22 / 50 ms at 6x on a loaded machine (the bare photo 17 / 17 ms); at 1280x720 the blur alone is 25 / 33 ms at 4x (area 60%: 21 / 33 ms). Software rendering is far slower than a phone's GPU, so these numbers are the worst case; the step-down above is the safety net. The title noise (`NoiseCanvas` 120x160 at 12 fps, scaled up) was measured too and costs about 2 ms on top of the bare photo at 1280x720, so it was left as it is. ### Screen transitions (#336)

The four screens (title, note before a shift, monitor, note after a shift) change with a dip to black: the old screen goes dark, the new one comes up from black. The usual change is 200 ms dark + 200 ms up (400 ms). Every start of a shift (note before it -> monitor, `memo-before` -> `shift`, and the result note's "once more", `result` -> `shift`) is slow, by kako-jun's request ("ゆっくり黒から監視画面が見えてくる、3倍くらい", 2026-11-12): 200 ms dark + 1000 ms up (1200 ms), so the monitor appears slowly out of the black. The lengths are set only in `transitionTiming(from, to)` in `src/utils/screenTransition.ts` (the veil's two CSS durations come from it, kept after the swap so the rise uses the same timing). The split was chosen by measuring the veil's computed opacity in a real browser: 100/1100, 200/1000 and 400/800 all rise alike, so the shortest dark that still hides the unmount of the note (200 ms, same as the other changes) was kept and everything else went to the rise. The game state is committed at once; `ScreenTransition` only decides what is shown. While the veil goes black it keeps rendering the old screen element in the same wrapper at the same place (never remounted, so it keeps its own state: camera, knobs, the pan of the title picture), with `inert` switched on and a window capture listener stopping keydown/keyup/keypress so that the old screen's global key handlers (it has old props) cannot drive the live game. The new screen is mounted when the veil's `transitionend` fires (a timer of 200 + 150 ms is the fallback), so a heavy mount cannot swap the screens before it is black. Neither picture can be pressed during the change, so a double tap cannot run an action twice. Consequence of committing at once: the game clock and spawns of a new shift start running while the veil goes black, so the first ~200 ms of the clock (the dark half; the rise is visible) is not seen. Accepted for the slow start too: the first anomaly comes at `firstAnomalyDelayMs` (12 s) and the note's hint subtitle starts when the monitor mounts, so nothing can appear or be reported before the picture is on its way up. In-screen changes (START OVER confirmation, report dialog, camera switch, language) are not screen transitions and keep their own motion. `prefers-reduced-motion` and `?transition=none` switch the fade off.

Comparing looks (dev server only; a production build ignores the parameter): `?transition=fade` (default), `?transition=cross` (the old screen fades away over the new one; dev only, with side effects: a second, remounted copy of the old screen lives for 400 ms, so two Cabinets and doubled window key handlers), `?transition=none` (cut).

## 10. Implementation Notes

- All tokens live in `src/index.css` under `:root`.
- Tailwind utility classes are allowed for layout, but **all colors and durations must come from CSS variables** (`text-[color:var(--text-hi)]`, `transition-[transform_var(--dur-fast)_var(--ease)]`, etc.). Inline-hex use is a lint smell.
- Components consume tokens directly; no per-component constant files.
- **State-layer mixing**: prefer `color-mix(in srgb, var(--semantic) <opacity%>, transparent)` over hand-rolled rgba literals.
- **Raw `rgba(0, 0, 0, …)` is permitted** for pure black-occlusion ramps (shadow gradients, vignettes) — these express geometry of light, not a brand color, and tokenizing them would over-couple. Anything else with brand intent must use a semantic token.
- **Bottom strip (#304)** (`.cabinet > .cabinet-foot`, `retro.css`): one row along the cabinet's bottom edge, speaker grille (`.speaker`) on the left filling the width, model plate (`model-plate.webp`, `alt` only) fixed at the right end, bottoms aligned (`align-items: flex-end`). `left: 4px; right: 6px` is deliberate (the cabinet face's bevel is wider on the right).
  - Height `--plate-h`: 20px on portrait (< 900 px; the smallest height at which the outlined "42" still reads at DPR 1; "Video Monitor CR-" is allowed to blur), 40px at >= 900 px. Portrait `.tube` constants subtract it as a separate term, so a height-limited picture is 20px shorter than without the strip (width-limited ones, about 412 x 915 and larger, are unchanged). `.cabinet` (portrait) / `.panel` (>= 900 px, divided by `--pz`) get bottom padding of the strip + 6px so nothing sits under it. `--pz` is the panel's zoom (1.3 from 1200 px, 1.45 from 1400 px), set at the same two breakpoints as `--col-min`.
  - Slots: always **two rows** (kako-jun, #304). `speaker_tile.webp` (27x42, two rows per tile) is scaled by `--hole-p` (row pitch; tile = 2 x pitch): 10px on portrait, 14px at >= 900 px (grille 28px tall inside the 40px strip). `background-repeat: round no-repeat` nudges the tile width so a whole number of slots fills the width: the right-end slot is never clipped and all slots share one shape. The nudge is within +-2% of the tile width at every width (measured +1.94% at 1024x768, -1.52% at 1280x720, -2.04% at 360).
  - >= 900 px: the strip spans the control-panel column. The 3:4 picture height `--tube-h` is `min(100vh - 16px, (100vw - 30px - --col-min) * 1679/1246)`, so on tall screens (900x1000, 1024x1366) the picture shrinks before the column gets narrower than `--col-min` (340px; 442px / 493px under the 1.3 / 1.45 panel zoom), which keeps the plate (155px) and the REPORT key on screen.
  - Not measurable in vitest/jsdom (no layout): `npm run check:foot` opens the game in a real Chromium at 12 sizes (360x640 ... 2560x1440) and checks strip / plate / panel inside the viewport, no overlap with REPORT, no scroll, two rows, `round`, whole slots. It is not in CI (needs a Chromium; `playwright` is an inline `uv` script dependency, not in package.json).
  - Title screen: `npm run check:title` (same style, 10 sizes x 2 languages; see §7).
- **App icons (#388)**: `public/` root (not `public/ui`, so they stay outside the 800 KB UI budget in `uiAssets.test.ts`), all cut from one master (the `a` whose bowl is an eye, `²` untouched; a later title swaps only the number) with Pillow LANCZOS only: `icon-512.webp` / `icon-192.webp` (any purpose; webp because the PNG was 405 KB at 512), `apple-touch-icon.png` (180), `favicon-32.png` / `favicon-16.png`. **Do not add maskable icons or an SVG icon**: Android draws a square frame around the splash screen for them; keep the manifest `icons` to the two `any` images. Dark cabinet colours (`#030a04`, cream text), no emoji, two keys always visible (ADD / LATER, Japanese 追加 / あとで; on iOS only LATER, with the steps "Share -> Add to Home Screen" as the text), each at least 44px. ## 11. Retro display reference

**Direction (kako-jun, 2026-10-30):** the game watches a corona-era underground arcade, so the _display_ should look like old physical surveillance hardware while the _interaction_ stays modern and phone-native (touch targets, gestures, readable controls). Retro is a rendering layer, not a behavior change.

**Reference:** `assets/reference/crt-monitor/panasonic-wv-bm140.jpg` — Panasonic WV-BM140 surveillance video monitor, photographed by kako-jun. Reference only: it is not bundled into the game (the part images below only resemble it), and the Panasonic mark must not be reproduced (use invented names, as with the signage baselines). EXIF is stripped; pixels are unchanged from the original.

What to take from it:

- **Screen:** rounded-corner rectangle (large radius), thick dark inner bezel, full-color picture (the reference unit is monochrome; the game is not), clearly visible horizontal scanlines, low contrast, soft glow.
- **Housing:** aged cream/beige matte plastic with a recessed frame around the tube.
- **Control strip:** square recessed power button with a red LED, slide switches, knobs with an indicator line, four numbered push buttons with arrow marks, a speaker slit grid, and silkscreened labels.

**Analog operation (kako-jun, 2026-10-30):**

- Corona Road is meant to be unusually fine-grained and hard, unlike click-only spot-the-difference games (target scale: see `prompts/README.md`). Operation should feel analog.
- Adjustments such as brightness are knobs: operated by touch (drag/rotate) but drawn as physical knobs.
- The picture stays in color. Analog noise is added and drifts subtly over time (not a visible loop, not frozen static).
- Rounded corners on the screen and on the parts.

**Monitor frame geometry (#283):** `bezel_mon.webp` is 1246x1679 and `.bezel` declares exactly that `aspect-ratio`, so `background-size: 100% 100%` is an unstretched fit (corners and grain stay round and square at every width; the phone height is the tube width divided by that ratio, and at 900 px and up the tube width is its height times it). The picture's four rim+recess bands are equal (99 / 99 / 100 / 99 picture px: left, top, right, bottom), so the frame looks equally thick on all sides. The opening is ONE numeric group (`--img-w/h`, `--open-l/t/r/b`, `--open-pad` on `.glass`): the glass box derives from it and the `clip-path` polygon is traced from the same alpha. `scripts/bezel-frame.py` ties all of it to the real picture: `check` (run by `npm run check:bezel`, vitest and CI) compares the group, the aspect and the polygon against the webp's alpha (polygon vs opening: max deviation within 1 picture px), and `apply` rewrites the group and polygon in `retro.css` after the picture is replaced.

Kept as CSS (not images): scanlines, noise, glow, vignette, OSD (REC / CAM n / subtitles), every label and number, the glass haze, (the sticky notes of the SELECT CATEGORY dialog are pictures, see the REPORT row of the component table, #346). The start screen and the result screen both use the new design.
