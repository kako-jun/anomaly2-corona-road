# セーブデータの設計

周回をまたぐ進行（見つけた異変の累計・ストーリーのフラグ・使用済みの会話）の保存方法。背景は `docs/story.md`、会話の仕組みは Issue #29。実装済みの範囲は末尾の「実装状況」、決まっていない項目は「未決」。

## 決定: localStorage に、バージョン付きの JSON を1キーで保存する

現行のゲームは何も保存していない（`localStorage` も IndexedDB も未使用、保存用の依存ライブラリなし）。静的ホスティングで、サーバーは持たない。

localStorage を選ぶ理由:

- データが小さい。累計の数、フラグ、使用済みの会話 ID で、数 KB から数十 KB。上限（約5 MB）に遠く及ばない。
- 同期 API で単純。起動時に1回読み、節目で書くだけで足りる。
- IndexedDB は、大きなデータ、バイナリ、検索、トランザクションが要るときに使うもの。いまは不要で、ライブラリ（idb、Dexie など）も増やさない。
- 消えやすさは、どちらでも同じ。サイトデータの削除、プライベートブラウズ、ブラウザによる長期未使用データの削除（Safari は約7日と言われる。要確認）が、どちらの保存先にも当てはまる。IndexedDB にしても解決しないので、「引き継ぎコード」で対処する（後述）。

## 保存するもの（スキーマ案 v1）

```json
{
  "v": 1,
  "foundTotal": 0,
  "foundIds": [],
  "loops": 0,
  "flags": {},
  "usedLines": {},
  "usedChatter": [],
  "pendingStories": [],
  "settings": { "brightness": 50, "contrast": 50 }
}
```

- `foundTotal`: 見つけた異変の累計（全プレイの合計）。同じ異変を何度見つけても数える（重複あり）。`flags.yaml` の `foundTotal` 条件で節目に使える。
- `foundIds`: これまでに見つけた異変の id の一覧（重複なし）。重複なしの異変の数は配列の長さ。`flags.yaml` の `foundUnique` 条件と「この異変を見つけたか」の判定に使う。台帳の全件でも約300個で、小さい。
- `loops`: 周回数。周回の定義は #29 で決める。
- `flags`: ストーリーのフラグ。キー体系は台詞台帳と一緒に決める。
- `usedLines`: 異変の id（`prompts/anomalies.yaml` の `id`）→ 使用済みの会話 ID の配列。異変ごとに複数通りの会話を重複させないため。
- `usedChatter`: 異変ごとの会話以外（オープニング・終了・中間コメント・雑談・フラグ会話・共通の誤報会話）の使用済みの ID。袋が空になったら、その袋の分だけ取り除いて補充する（全員分を取り除かない）。
- `pendingStories`: 立ったが、まだ再生していないフラグ会話のフラグ名。フラグが立った事実は `flags` に、会話が未再生であることはここに分けて持つ。そのフラグ会話の最初の1行を表示した時に取り除く。再生前にプレイが終わっても残り、次回の開始時に再生される。ない古いセーブは空として読む（`v` は上げない）。
- `settings`: つまみの位置など（任意）。

異変の id は台帳が正本なので、ここでは複製せず、参照するだけにする。

## 規則

1. **薄い保存モジュール1つに閉じ込める**（例: `src/utils/saveData.ts`）。ゲーム側は `load()` / `update(fn)` だけを使う。将来 IndexedDB に替えるときは、ここだけを差し替える。
2. **キーは1つ**（例: `corona-road:save`）。全体を1回で書き、部分書き込みで壊れないようにする。
3. **読み込み時に検証する**。壊れていたら新規データで開始し、壊れた元は別キー（`corona-road:save:broken`）に1つだけ退避する。**ただし、この版より新しい `v` のセーブは壊れた扱いにしない**: 退避も上書きもせず、その回は保存なしで動き、規則6の案内（`canPersist()` が false）を出す。
4. **バージョン移行**: `v` を見て、古い版から順に移行する関数を並べる。
5. **書き込みのタイミング**: 正しい報告で累計が変わったとき、フラグが立ったとき、プレイの終了時（勝敗・エンディング）。毎フレームは書かない。
6. **保存できない環境**（プライベートブラウズなどで例外）: 例外を捕まえ、メモリ上だけで動き続ける。「進行を保存できません」という案内を常時表示する（案内を隠さない方針）。
7. **複数タブ**: 保存時に最新を読み直してマージする。データは増える一方（累計は増加、フラグと使用済みは追加のみ）なので、`foundTotal` は大きいほう、`foundIds` とフラグと使用済みと `pendingStories` は和集合で、衝突なく統合できる。会話の使用済みを書くときは、保存済みとの和集合にし、袋の補充でその会話自身が取り除いた id だけを除く。
8. **永続化の要求**: 初回の保存後に `navigator.storage.persist()` を呼ぶ。許可されれば削除されにくくなるが、保証はされない。
9. **引き継ぎコード**: 設定の部品に、セーブの書き出し（JSON を Base64 の文字列にしてコピー）と読み込み（貼り付け、検証、確認のうえ上書き）を用意する。端末の移動や、データ消失への対処になる。
10. **不正編集は防がない**。単独プレイのローカルデータなので、最後のフラグを手で立てられても構わない。ただし、検証で壊れたデータは弾く。

## IndexedDB に切り替える条件

データが約1 MB を超える、または画像や音声などのバイナリをユーザー側に保存したくなったとき。保存モジュールを差し替えるだけで済むようにしておく。

## 実装状況（#74）

- 保存モジュール `src/utils/saveData.ts`、記録 `src/utils/shiftProgress.ts`（正しい報告で累計・重複なしの数・フラグ、プレイ終了で周回、開始時に周回由来のフラグ）、会話の使用済みは `useSubtitle` が、会話の最初の1行を表示した時に保存（未再生のフラグ会話は `pendingStories`）。
- 周回: 夜明け・撤収・エンディング（子供発見後の異変を一件も報告せず時間切れ、#86）のどれでも1進める。エンディング専用の保存項目はなく、`child` フラグは残るので、次の勤務も子供発見後の勤務として始まる（異変が増える・再びエンディングになりうる）。
- 保存できない環境の案内（規則6）は `SaveNotice`（開始・プレイ・結果の各画面に常時）。書き込みだけ失敗する環境（容量超過など）も開始画面で分かるよう、起動時に専用キー `corona-road:save:probe` へ書いて消す `probe()` を1回試す（セーブ本体のキーには触れない）。案内は画面に重ねず、筐体・開始画面の下に通常フローで積む。
- 未実装: 引き継ぎコード（規則9）、設定（つまみ）の保存、令和の異変の印（`reiwaFound` は印が付くまで立たない）。
