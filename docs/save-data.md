# セーブデータの設計

周回をまたぐ進行（見つけた異変の累計・ストーリーのフラグ・使用済みの会話）の保存方法。背景は `docs/story.md`、会話の仕組みは Issue #29。実装済みの範囲は末尾の「実装状況」、決まっていない項目は「未決」。

## 決定: localStorage に、バージョン付きの JSON を1キーで保存する

現行のゲームは何も保存していない（`localStorage` も IndexedDB も未使用、保存用の依存ライブラリなし）。静的ホスティングで、サーバーは持たない。

localStorage を選ぶ理由:

- データが小さい。累計の数、フラグ、使用済みの会話 ID で、数 KB から数十 KB。上限（約5 MB）に遠く及ばない。
- 同期 API で単純。起動時に1回読み、節目で書くだけで足りる。
- IndexedDB は、大きなデータ、バイナリ、検索、トランザクションが要るときに使うもの。いまは不要で、ライブラリ（idb、Dexie など）も増やさない。
- 消えやすさは、どちらでも同じ。サイトデータの削除、プライベートブラウズ、ブラウザによる長期未使用データの削除（Safari は約7日と言われる。要確認）が、どちらの保存先にも当てはまる。IndexedDB にしても解決しないので、「引き継ぎコード」で対処する（後述）。

## 保存するもの（スキーマ案 v1）

```json
{
  "v": 1,
  "foundTotal": 0,
  "foundIds": [],
  "loops": 0,
  "flags": {},
  "usedLines": {},
  "usedChatter": [],
  "pendingStories": [],
  "pendingMemoFlags": [],
  "shownMemoFlags": [],
  "pendingMemos": [],
  "shownMemos": [],
  "endingReached": false,
  "epoch": 0,
  "lastShift": { "found": 9, "fresh": 4, "misreports": 1, "durationMs": 480000, "closing": "dawn", "raised": [] },
  "settings": { "language": "ja" }
}
```

- `foundTotal`: 見つけた異変の累計（全プレイの合計）。同じ異変を何度見つけても数える（重複あり）。`flags.yaml` の `foundTotal` 条件で節目に使える。
- `foundIds`: これまでに見つけた異変の id の一覧（重複なし）。重複なしの異変の数は配列の長さ。`flags.yaml` の `foundUnique` 条件と「この異変を見つけたか」の判定に使う。台帳の全件でも約300個で、小さい。
- `loops`: 周回数。周回の定義は #29 で決める。
- `flags`: ストーリーのフラグ。キー体系は台詞台帳と一緒に決める。
- `usedLines`: 異変の id（`prompts/anomalies.yaml` の `id`）→ 使用済みの会話 ID の配列。異変ごとに複数通りの会話を重複させないため。
- `usedChatter`: 異変ごとの会話以外（オープニング・終了・中間コメント・雑談・フラグ会話・共通の誤報会話）の使用済みの ID。袋が空になったら、その袋の分だけ取り除いて補充する（全員分を取り除かない）。
- `pendingStories`: 立ったが、まだ再生していないフラグ会話のフラグ名。フラグが立った事実は `flags` に、会話が未再生であることはここに分けて持つ。そのフラグ会話の最初の1行を表示した時に取り除く。再生前にプレイが終わっても残り、次回の開始時に再生される。ない古いセーブは空として読む（`v` は上げない）。
- `pendingMemoFlags` / `shownMemoFlags` / `pendingMemos` / `shownMemos`（#325、リザルトの捜査メモの出し分け）: 仮説フラグ（台帳 `memo_flag`、`reiwa: true` の異変は `reiwa`）は、その異変を報告した時に `pendingMemoFlags` へ立った順に積む（未表示。表示済みの名前は積まない）。一言メモ（台帳 `memo` のある異変）は、報告した時にその異変 ID を `pendingMemos` へ積む。勤務が終わる時（`recordShiftEnd`）に、種類ごとに1つずつ選んで未表示から表示済みへ移す: 仮説は段階（`knownFrom`）に届いたものの中で最も古い1つ、一言メモは持ち越し分から無作為に1つ（乱数の種はその時点のセーブ（`epoch`・`loops`・`foundTotal`・`foundIds`・`pendingMemos`）から決める。`memoSeed`）。選んだ結果は `lastShift.memoFlag` / `lastShift.memo` に書くので、リザルトを開き直しても同じメモが出る。選ばれなかった分は未表示のまま次の勤務のリザルトへ持ち越す（見つけた夜でなくても出る）。一度表示済みにしたものは二度と出さない。台帳から消えた ID・未知のフラグ名は選ばれず、読み込みも落ちない。ない古いセーブは4つとも空として読む（`v` は上げない）。マージは和集合で、表示済みは未表示に勝つ（片方のタブで出したものをもう片方で出さない）。ERASE ALL（`resetProgress`）は4つとも空に戻す。
- `endingReached`: 特殊エンディング（#86）に到達した印（#294）。true のセーブでは勤務を始められず、タイトルは「START OVER」だけになる。欠落した古いセーブは false として読む（`v` は上げない）。複数タブのマージは、同じ `epoch` のあいだは OR。
- `epoch`: リセットの世代番号（安全な整数 `Number.isSafeInteger`、欠落した古いセーブは 0 として読む。`v` は上げない）。START OVER のたびに +1 する。マージでは `epoch` の大きい側を丸ごと採用し、小さい側の中身（進行・使用済み・`endingReached`）は捨てる（`settings` は採用側に無ければ小さい側のを残す）。
- 捜査メモの段階（`stageOf`、#297）: セーブから `start`（`loops` と `foundTotal` が0＝一度も遊んでいない）、`none`（遊んだがフレームが埋まっていない）、`elder1`〜`elder3`・`child`（立っている最も進んだ段階フラグ）を導く。文言はその段階で刑事が知っていることだけ（各文の `knownFrom`、`src/data/investigationNotes.ts`）。
- `lastShift`: 直近に終わった勤務の記録（任意。捜査メモ #297 の「前回の夜」と結果画面に使う）。`found`＝正しい報告の数（重複あり）、`fresh`＝その勤務で初めて見つけた異変の数（重複なし。0 なら「新しい手がかりなし」）、`misreports`、`durationMs`（現実の経過ミリ秒のまま保存。夜明け・真エンディングは 480000 に丸める。捜査メモの「勤務」欄は表示時にゲーム内時刻へ変換する: 夜明け・真エンディング=「06:00まで」、撤収=`msToGameTime(durationMs)` を使った「01:20で撤収」。`fmtShiftEnd`）、`closing`（`dawn`/`withdraw`/`ending`）、`raised`（その勤務で立った段階フラグ `elder1..3`・`child`）、`memoFlag` / `memo`（その勤務のリザルトに出すメモ。任意、#325）。勤務終了時（`recordShiftEnd`）に書く。欠落した古いセーブは「なし」、壊れていれば捨てるだけでセーブ全体は弾かない。マージでは周回数の大きい側（同じなら `b`）。`v` は上げない。
- `settings`: 設定（任意）。`language`（`ja`/`en`。#292。**将来の設定画面用に予約。現在は書き込まず、読み取っても使わない**（言語は起動のたびにブラウザの言語から決める）。旧セーブにあっても落ちず、無視する）、`brightness`・`contrast`（つまみの位置。未実装）。各項目は単独で欠落してよい。マージは項目ごとに `b` が勝つ。START OVER でも残る。

異変の id は台帳が正本なので、ここでは複製せず、参照するだけにする。

## 規則

1. **薄い保存モジュール1つに閉じ込める**（例: `src/utils/saveData.ts`）。ゲーム側は `load()` / `update(fn)` だけを使う。将来 IndexedDB に替えるときは、ここだけを差し替える。
2. **キーは1つ**（例: `corona-road:save`）。全体を1回で書き、部分書き込みで壊れないようにする。
3. **読み込み時に検証する**。壊れていたら新規データで開始し、壊れた元は別キー（`corona-road:save:broken`）に1つだけ退避する。**ただし、この版より新しい `v` のセーブは壊れた扱いにしない**: 退避も上書きもせず、その回は保存なしで動き、規則6の案内（`canPersist()` が false）を出す。
4. **バージョン移行**: `v` を見て、古い版から順に移行する関数を並べる。
5. **書き込みのタイミング**: 正しい報告で累計が変わったとき、フラグが立ったとき、プレイの終了時（勝敗・エンディング）。毎フレームは書かない。
6. **保存できない環境**（プライベートブラウズなどで例外）: 例外を捕まえ、メモリ上だけで動き続ける。「進行を保存できません」という案内を常時表示する（案内を隠さない方針）。
7. **複数タブ**: 保存時に最新を読み直してマージする。データは増える一方（累計は増加、フラグと使用済みは追加のみ）なので、`foundTotal` は大きいほう、`foundIds` とフラグと使用済みと `pendingStories` は和集合で、衝突なく統合できる。ただし**リセットは「減る」操作**なので、この和集合・最大値のマージでは表せない。古いタブが旧い進行をメモリに持ったまま保存すると、リセットが打ち消されてしまう。そこで `epoch` を使う: リセットで `epoch` を +1 して書き、以後のマージでは `epoch` が大きい側（リセット後）が勝つ。古いタブの旧世代の中身は破棄される。`epoch` が同じなら上の規則どおり統合する。古いタブには `storage` イベントで変化を伝え、タイトルを読み直して描き直す（`App`）。会話の使用済みを書くときは、保存済みとの和集合にし、袋の補充でその会話自身が取り除いた id だけを除く。
8. **永続化の要求**: 初回の保存後に `navigator.storage.persist()` を呼ぶ。許可されれば削除されにくくなるが、保証はされない。
9. **引き継ぎコード**（#84）: タイトル画面の TRANSFER SAVE から開くパネルで、セーブの書き出し（EXPORT。JSON を UTF-8 の Base64 にして表示し、COPY でコピー）と読み込み（IMPORT。貼り付け、検証、要約を見せる確認のうえ REPLACE で上書き）ができる。端末の移動や、データ消失への対処になる。詳細は末尾の「引き継ぎコードと `epoch`」。
10. **不正編集は防がない**。単独プレイのローカルデータなので、最後のフラグを手で立てられても構わない。ただし、検証で壊れたデータは弾く。

## IndexedDB に切り替える条件

データが約1 MB を超える、または画像や音声などのバイナリをユーザー側に保存したくなったとき。保存モジュールを差し替えるだけで済むようにしておく。

## 実装状況（#74）

- 保存モジュール `src/utils/saveData.ts`、記録 `src/utils/shiftProgress.ts`（正しい報告で累計・重複なしの数・フラグ、プレイ終了で周回、開始時に周回由来のフラグ）、会話の使用済みは `useSubtitle` が、会話の最初の1行を表示した時に保存（未再生のフラグ会話は `pendingStories`）。
- 周回: 夜明け・撤収・エンディング（子供発見後の異変を一件も報告せず時間切れ、#86）のどれでも1進める。エンディング（`closing==='ending'`）に到達すると `endingReached` を保存する（#294）。到達の保存は時間切れ判定（`closing==='ending'` で終了）の時点で行うので、closing の会話の途中でタブを閉じても到達は残る。以後このセーブでは `startGame` が何もせず、結果画面の手書きの操作は「タイトルへ」（英: Back to title）、タイトルは「START OVER」だけを出す（`StartScreen` の `endingReached`）。START OVER は確認（"All progress will be erased"・ERASE ALL / CANCEL。確認に入ると CANCEL に、CANCEL か Escape で START OVER に、ERASE 後は START SHIFT にキーボードのフォーカスが移る）を1回挟み、`resetProgress()`（`shiftProgress.ts`）が `settings` 以外の全項目（累計・重複なしの id・周回・`child` を含むフラグ・使用済みの会話・未再生のフラグ会話・`endingReached`）を初期値に戻し、`epoch` を +1 する。印のない既存セーブは従来どおり。
- 保存できない環境の案内（規則6）は `SaveNotice`（開始・プレイ・結果の各画面に常時）。書き込みだけ失敗する環境（容量超過など）も開始画面で分かるよう、起動時に専用キー `corona-road:save:probe` へ書いて消す `probe()` を1回試す（セーブ本体のキーには触れない）。案内は画面に重ねず、筐体・開始画面の下に通常フローで積む。
- 引き継ぎコード（規則9、#84）: `src/utils/transferCode.ts`（`encodeSave`・`parseCode`・`importedSave`・`applyImport`）と `TransferPanel`（`StartScreen` の TRANSFER SAVE キーから開く）。

## 引き継ぎコードと `epoch`

- 形式: セーブ全体（`SaveData`）の JSON を UTF-8 にして Base64（標準アルファベット）。コード自体にバージョン印はなく、中の `v` で見る。貼り付けでは空白・改行を無視する。メモの列などが無い古いセーブのコードは、欠けた項目を空として読む（`validateSave` の互換）。
- 読み込みの弾き方（理由は画面に出し、何も変えない）: 空、Base64 でも JSON でもない、`validateSave` を通らない（壊れた・欠けたコード）、この版より新しい `v`。大きさの上限(定数は `saveData.ts` の `SAVE_LIMITS` と `transferCode.ts` の `MAX_CODE_CHARS` の1か所): 貼り付けは40万文字まで(超えたら中身を読まずに「長すぎる」と出す。実際のセーブは数十KB)、配列は2万件、`flags`/`usedLines` のキーは2000個、1つの文字列は200文字、`loops`/`foundTotal` は10億、`epoch` は10億。上限は通常の読み込み(localStorage)にも効く。`epoch` が上限以上のコードは弾き、リセットと取り込みの +1 も上限で止める(次の読み込みで拒否されて進行が退避されないため)。`v` の古いコードは `validateSave` が移行する（現状は v1 のみ）。
- 取り込み: 確認で「コードの中身」と「この端末の現在の進行」の要約を並べて見せ、REPLACE で初めて書く（CANCEL・Escape では何も変えない）。進行（累計・id・周回・フラグ・使用済み・`pendingStories`・メモの4つの列 `pendingMemoFlags`/`shownMemoFlags`/`pendingMemos`/`shownMemos`・`lastShift`（`memoFlag`/`memo` を含む）・`endingReached`）はコード側を丸ごと採用し、端末側とはマージしない。`settings` は端末側を残し、端末側に無ければコード側を使う。
- `epoch = max(local, imported) + 1` で書く。これで他タブの旧メモリ（`epoch` が小さい）は保存時のマージで負け、取り込みが復活で打ち消されない。
- 決定（2026-11-12 kako-jun）: `endingReached` は現時点では不要だが、将来のため含める。含めた場合、START OVER で消した端末に消す前のコードを読み込むとエンディング到達が戻る。確認画面の要約に "investigation closed" と出る。
- `endingReached` はコードに含まれる（セーブ丸ごとの原則）。このため、特殊エンディング後に START OVER で消した端末に、消す前のコードを読み込むと、エンディング到達の状態が戻る。保存に失敗した(容量超過・保存できない環境)ときは取り込みを成功にせず、理由を出して元の進行を戻す。パネルは `aria-modal` に合わせ Tab を中に閉じ込め、開くと貼り付け欄、閉じるとキーにフォーカスする。`canPersist()`(保存できない案内)は最後の読み書きの結果に従い、保存に成功すれば消える(一度の失敗で張り付かない)。取り込みの成否は書き込みの戻り値で決める。端末の `epoch` が上限に達していると取り込みの `epoch` が同値になり「後に実行した方が勝つ」は成り立たないが、実プレイでは到達しない。ERASE ALL は取り込みを取り消さず、取り込みも ERASE ALL を取り消さない（後に実行した方が `epoch` で勝つ）。
- 置き場所: タイトル画面の右上に TRANSFER SAVE キー。パネルには操作の説明を常に出す。ゲーム中・結果画面には置かない。

## 既知の制約

- リセット後（`epoch` ≥ 1）の古いタブが生きたまま storage が消える／壊れ、新しいタブが `epoch` 0 で進行を溜めた場合、古い `epoch` 1 のタブの書き込みが新しい進行を丸ごと捨てる。低頻度で、現状は対策なし。
