# Corona Road anomaly creation

Use this skill when planning or producing an image-based anomaly for this game. The goal is a repeatable record from idea through review, with the existing camera photo remaining the authoritative background.

## References

- Read [`prompts/camera-element-inventory.md`](../../../prompts/camera-element-inventory.md) for the single source of truth for camera photos, visible elements, stable IDs, and approximate bounds.
- Open the matching `prompts/atlas/camNN.svg` for a visual index of those IDs; regenerate maps with `npm run build:camera-atlas` after changing the inventory.
- Read [`prompts/candidate-pool.md`](../../../prompts/candidate-pool.md) for photo-specific unselected ideas, the Showa-theme candidates, the runtime/audio/UI anomaly stock with its phase-allocation guide, and the finalized-but-unproduced production specs (small objects and large-area changes: box, prompt, visibility notes); remove a selected row when promoting it into `anomalies.yaml`.
- Follow [`prompts/README.md`](../../../prompts/README.md) and [`prompts/base-template.md`](../../../prompts/base-template.md) for prompt conventions.
- The current game camera mapping is in `src/utils/gameConfig.ts`; the WebP exports are in `public/images/`.

## Workflow

1. **Resolve the referenced object.** When the user names a stable element ID, use that exact entry. When they describe an object naturally (for example, “the pink pot by the right wall”), match it against the inventory's camera, reading-order description, and coordinates. State the matched camera/element ID and bounds before production. If two entries still fit, ask which one rather than guessing. The inventory is the only source for element descriptions and coordinates; do not create duplicate descriptions elsewhere.
2. **Inspect the whole frame before ideation.** Sweep the image in reading order: top to bottom, and within each horizontal band left to right. Check the element inventory against the actual frame, including objects, surfaces, fixtures, sign/text, openings, lights, shadows, reflections, and notable empty/dark areas. Record uncertain readings as uncertain rather than guessing. The camera's game label may not match the photographed scene. Build ideas only from visible affordances. Mark unsupported ideas as runtime/hybrid instead of forcing them into the photo.
3. **Define one anomaly.** Record a stable anomaly ID, source baseline, camera ID, element ID, category, anomaly type, phase, intended subtlety, exact changed element, and short rationale. Do not combine unrelated changes in one generation.
   - **Placement rule (kako-jun, 2026-11-02; the authority is "配置の基準" in `prompts/README.md`).** Within one camera, anomalies must not overlap in coordinates and must not cluster ("ここばっかり" is a defect). Before choosing a place, list every overlay of the same `camera_id` in `prompts/anomalies.yaml` (`overlay_origin` + `dimensions`) with a short `uv run --with pyyaml python3` script, and measure that the candidate rectangle (object plus shadow) neither overlaps nor comes within about 30 px of any of them. Do not stack changes on an object that already hosts anomalies (a crate, a door, a sign), even as a deliberate Showa/Reiwa contrast. If the candidate collides, move it to another place or element, then record the nearest existing id and distance in the entry's `note`. Pre-existing neighbours must be re-measured from the final overlay's alpha bbox, not from the intended object box, because the feathered edge widens it. **Exception (kako-jun, 2026-11-04): large-area anomalies (a whole wall of posters, a whole floor stain, a whole ceiling covering; alpha bbox about 1/8 of the frame or more) may overlap small anomalies' coordinates; two large-area anomalies of the same camera must not overlap either, unless they use the same surface and are declared mutually exclusive in their notes (the game spawns at most one undetected anomaly per camera at a time, see `spawnAnomaly` in `src/hooks/useGameState.ts`; e.g. CR-LG-08-01 and 08-02). See "配置の基準" in `prompts/README.md`, which is the authority.**
   - **Small props go on wide surfaces.** A small prop on a small piece of furniture (a phone on a stool seat, a can on a crate, a mask on a door handle) came out too small to see and collided with older anomalies. Prefer the large floor area, in the foreground, with a dark contact shadow and a clear tone difference from the ground; avoid specular light pools where white or silver props dissolve.
4. **Specify location reproducibly.** Use the selected element's normalized coordinates `(x,y)` from 0 to 1000, origin at top left. Refine its box around the actual object at full resolution. Record the element ID and final mask/box in the anomaly entry; do not copy the element's description into a second inventory. A polygon or hand-painted mask is preferred for irregular objects.
5. **Generate a proposal.** Attach the baseline and ask for only the defined change. Tell the image model to preserve framing, perspective, lighting, texture, grain, compression, and every other object. Treat the result as a source layer, never as the finished full frame. This source layer and the mask are working files: discard them after verification (see "作業置き場(experiments/)"); only the transparent WebP is kept.
6. **Composite into the baseline.** Align the generated layer to the baseline without resizing or warping the baseline. Build a mask that covers the changed object and its immediate contact shadow/reflection when needed. Use a softly feathered, semi-transparent gradient transition around that mask so the insertion blends into the surveillance image. Keep mask alpha exactly zero outside the documented transition boundary. Do not apply global color correction to the baseline. The reproducible tool is `scripts/composite-anomaly.py` (dependencies are declared inline, so `uv run` is enough): `uv run scripts/composite-anomaly.py --base public/images/camN.webp --gen <generated.png> --box x1,y1,x2,y2 --out assets/anomaly-overlays/camNN/<slug>.webp [--preview <work>.png]`. The box is in baseline px. Do not hand-type px for a catalogued element: pass `--element CAM01-E12` instead of `--box` (ID from `prompts/camera-element-inventory.md`; `uv run scripts/composite-anomaly.py --list-elements CAM01` lists IDs with px boxes; `--margin <px>`, default 8, widens it; the CAM number must match `--base`; the JSON report records element_id, its description and box_px_used for the ledger; `--check-inventory` validates all conversions). Tune with `--threshold/--dilate/--feather` (a pale-on-pale change may need a lower `--threshold`). It aligns the generated image (translation only, estimated from outside the box), cuts the changed area into a feathered irregular mask, and prints a JSON report for steps 7-8: reconstruction match, nothing changed where alpha is 0, changed pixel count, bbox/origin/dimensions (also as ledger-format strings), and redraw/no-change detection. `fail` exits 2 and writes no WebP; read `warn` before accepting. The `--preview` composite is a work file, never committed. Verify the tool itself with `uv run scripts/composite-anomaly.py --selftest`.
   - **Large-area anomalies (a whole wall, floor or ceiling; 1/8 of the image or more, see `prompts/README.md` "配置の基準") use `scripts/composite-polygon.py`, not the diff tool.** A diff against the baseline with a low threshold picks up floor and wall grain and balloons; this tool takes the polygon as the truth and has no threshold. `uv run scripts/composite-polygon.py --selftest` verifies it. All coordinates are baseline px; every subcommand prints a JSON report and `fail` exits 2 without writing the output.
     - `crop --base public/images/camN.webp --crop x1,y1,x2,y2 --out <work>.png` makes the 3:2 (1536x1024) input for the image model from the face plus margin (the crop must already be 3:2, otherwise it fails instead of distorting). A tall face is split into an upper and a lower crop and generated separately.
     - `restore --base <full-size png> --gen <generated.png> --crop x1,y1,x2,y2 --out <full>.png` scales the generation into that crop and pastes it into the full frame (outside the crop stays the base). Apply it once per crop, feeding each output back as the next `--base` (upper half, then lower half). When the two crops overlap, add `--blend-px N [--blend-edges t|b|l|r...]` to the later one: it fades in linearly over what the earlier paste put there (default edge `t`), so the join has no seam.
     - `tile --base ... --material m.png [m2.png ...] --quad "tl tr br bl" --cols N --rows M [--gap --rot --scale-jitter --bright-jitter --seed --layout grid|scatter --shade 0..1 --polygon-out poly.json] --out full.png` lays a separately generated material (paper, photo, lantern) onto the face with a perspective that matches the quad (draw the quad along the tile joints / shutter edges first; the lattice plan comes before the pixels). `--seed` reproduces the jitter. `--shade` multiplies the baseline's low-frequency light onto the tiles. The output is a full frame, usable as `--gen`. **The quad must be clockwise on screen (y down): top-left, top-right, bottom-right, bottom-left**; the material's top-left goes to the first point. Any other order is rejected (it would mirror or transpose the material). `--polygon-out poly.json --polygon-append` adds each run's quad to the same file, so several tile runs (chained: the next run's `--base` is the previous output) accumulate their faces for one `cutout`.
     - **Sprites that are not photos (clock hands, marks)**: draw them with a separate PIL script into a transparent PNG and pass it as `--material` with `--rot 0 --scale-jitter 0 --bright-jitter 0` (CR-LG-07-01: one `tile` run for the large hands, a second run for the medium ones, `--cols 1 --rows 1` for a single sprite; the sprite script is a work file in `experiments/`, never committed).
     - `blend --base <full.png> --layer <full.png> --mode multiply|screen|overlay|normal --opacity 0-1 [--polygon ... --hole ... --feather σ --layer-norm --layer-blur σ --layer-brightness g] --out full.png` puts one full frame over another inside an optional mask, for the finishing steps of the spec: restore the reflection band with `--mode screen --layer <baseline> --polygon <band>`; lay the wall texture on pasted paper with `--mode multiply --layer <baseline> --layer-norm` (the layer is divided by its per-channel median, so it adds texture but keeps the average brightness); put a part of the floor's light/shade on a tiled floor with `--mode multiply --layer <baseline> --layer-blur 8 --layer-norm --opacity 0.5`. Nothing outside the mask changes (`pixels_changed_outside_mask`).
     - `flip --base <full.png> [--source <full.png>] --axis-y Y --region "x,y ..." [--hole ... --brightness 0.6 --opacity 0.7 --blur 1.5 --feather σ] --out full.png` is the water mirror: inside the region, row y shows row 2*Y-1-y of `--source` (default `--base`; pass the baseline to reflect the untouched scene), darkened and softened. Region pixels whose mirrored row lies outside the image stay unchanged and are counted in the report.
     - `cutout --base ... --gen <full.png> --polygon "x,y x,y ..."|poly.json [--hole "..."] [--feather 2] --out assets/anomaly-overlays/camNN/<slug>.webp [--preview <work>.png]` cuts the polygon out of `--gen` as is (no difference threshold), alpha exactly 0 outside the polygon, an inward feather ramp on the edge. `--polygon` may be repeated (or the JSON may hold `{"polygons": [...]}` / a list of `{polygon, holes}` items): the polygons are united into one overlay. `--hole` (repeatable, or `holes` per item in the JSON) keeps windows and small props untouched. Self-intersecting (bow-tie) polygons, nan/inf or absurd coordinates, and polygons entirely outside the frame are rejected. The report has `overlay_origin`/`dimensions` (and `_str`) for the ledger; measure the registered bbox from this report, not from the quad. It warns when the overlay's **bbox** area (`dimensions`, also in `bbox_area_frac`; the same basis as the docs' "1/8") is below 1/8, and names that basis in the message (the mask pixel area is reported separately).
     - **Image sizes**: `cam2`-`cam5` are 676x900, the others 675x900. Use the real size (`--list-elements CAMNN` prints it) when writing crops and polygons; the prompt specs say 675x900 everywhere (candidate-pool.md's common policy needs the correction, tracked separately).
     - Pick the polygon along stopping lines (floor/wall contact, skirting, frame, pillar edge). For a generated whole-frame result (lanterns, footprints), pass the generation (or its `restore` output) as `--gen` and draw the polygon around the face; for a repeated material, run `tile` first and feed its `--polygon-out` to `cutout`.
   - Lessons from batch production (read before generating):
     - A `fail` does not need a new generation: re-run the tool on the same `--gen` with a different `--threshold`/`--margin` (try 8/12/16/18). Thin lines and low-contrast changes work around 12; 8 tends to fail on redraws outside the box; a pale-on-pale or whole-frame redraw may need a higher value. On wide elements (whole floor, whole ceiling) a low threshold yields a huge overlay, so narrow it with `--box`.
     - Small changes (a digit, one brick, a small round sign) are usually ignored by a full-frame generation. Crop about 6x around the target, edit the crop with the image model, resize it back and paste it into the baseline PNG, then use that pasted full frame as `--gen`.
     - Feed the enlarged crop to the image model at 1536x1024 (3:2) and say "keep the same framing and zoom; do not recompose, re-crop or enlarge". A 900x600 input made the model re-zoom and re-frame all three takes, which then could not be pasted back. Always start the model with an explicit `$imagegen` (without it a forged PNG comes back; see the `/image` skill). Make three takes and pick by eye.
     - Keep `--box` tight around the object and its contact shadow. A wide box makes the overlay pick up the re-grained floor and grow far beyond the object (a 14x45 px bottle became 52x74), which then collides with neighbours. After compositing, measure the overlay's alpha bbox, not the box.
     - Props that are too faint fail the visibility floor: raise the size (about 1.4x) and contrast (bright highlight, dark outline, strong contact shadow) in the prompt rather than lowering the floor. Tiny props such as an earbud need about 2.5x exaggeration to stay above it. Silver or white props against a bright wall or light pool dissolve; lay them on a dark floor tile.
     - Ask the model for a plain, unmarked object ("completely blank, no label band, no markings") and look at ring-pulls, caps and labels in the result: stray letter-like engravings appear (reject those takes).
     - The image model sometimes returns a corrupt PNG (0 bytes or a few KB). Check file size and `file` output (genuine results are about 1 MB or more), and retry. Convert the baseline webp to PNG before passing it with `-i`.
     - Correcting an inventory or ledger offset never needs image generation: fix the inventory coordinates/description or the ledger element_id/note; do not regenerate overlays.
     - The inventory was audited against the real images once (the fixes are in the git history of `prompts/camera-element-inventory.md`, not here); a few low-confidence boxes may still be off. Before writing prompt coordinates, confirm the real position on an enlarged crop. Adding an explicit negative condition ("do not touch X") reduces misplaced edits.
7. **Review the result.** Compare baseline and composite at the same dimensions. Inspect a blink/A-B view and a difference image. Confirm that every changed pixel lies inside the mask/transition envelope (a working concept, not a stored file; see "作業置き場(experiments/)"); confirm no unrelated object, sign, camera framing, or overlay changed. If the changed region is too large to blend without collateral edits, regenerate or edit the local region manually.
8. **Register only after review and a visibility check.** Registering includes a mandatory visibility check: once the entry is in `anomalies.yaml`, run `uv run scripts/check-visibility.py --id <ledger id>`. The floor is defined only in `prompts/README.md` ("視認性の基準"); this skill does not restate it. If it is below the floor, strengthen the change (bigger, darker, flatter area) and regenerate, or remove the entry and its overlay and return the idea to `candidate-pool.md`. Save the cropped transparent overlay and its placement as the game asset, and update the anomaly record with the selected element ID, final mask/box, paths, dimensions, and review status. Keep runtime-only effects out of the image-variant queue.

## Record fields

For each candidate/variant, maintain:

`id`, `camera_id`, `element_id`, `base_photo`, `mask_box_1000`, `category`, `anomaly_type`, `phase`, `subtlety`, `description`, `generation_prompt`, `overlay`, `overlay_origin`, `dimensions`, `review_status`, `notes`.

Use `planned`, `generated`, `composited`, and `reviewed` as distinct states. Never mark an AI-generated full frame as reviewed merely because the requested object looks right.

## Constraints

- The baseline is authoritative. Preserve all pixels outside the documented mask transition envelope.
- The feather is a local edge treatment, not permission for broad transparent overlays or global retouching.
- Check whether readable signage is fictional/public-safe before creating public variants. Keep sign sanitization as its own edit, separate from the anomaly.
- The eight processed `public/images/cam*.webp` files are the complete camera-photo set and the authoritative baselines for anomaly variants.
- Coordinate boxes are normalized so they survive resolution changes. Convert them to pixels only for the selected source dimensions and record those dimensions.

## 昭和の時間が戻る異変

この作品では、懐かしく寂しい日常が一瞬戻る方向を優先する。閉店した店が営業する、壊れていた物が直る等、写真で確認できる現状から一つだけ変える。怖がらせる小道具を前提にしない。核となる変化は「閉店した店が再び営業し、壊れたものが直り、失われた日常が一瞬戻る」で、広告などの小道具は補助でありテーマの中心にしない。修復は元写真で破損が確認できる箇所を選んでから制作し、破損を想像で決めない。『既に存在した物の変化』と『追加』を混同しない。小物は実ゲームの表示寸法で視認性を検証する。公開用 baseline の店名・マークは kako-jun の他作品のパロディにし、Corona Road の名前は維持する。最初の本命は「閉じたシャッターが少し開き暖かな店内光が漏れる」。候補は `prompts/candidate-pool.md` の「昭和テーマ候補」を参照（制作状態は `prompts/anomalies.yaml` が正本）。

生成結果が全体を描き直しても、元画像を下地とし、生成画像を元の寸法・構図に位置合わせして対象と必要な光・影だけをマスクで重ねる。境界は徐々に透過させ、マスク外は必ずゼロにする。床目地やシャッターの線を確認し、ずれが見える場合は位置合わせやマスクを調整する。PNGなどロスレスで保存し、マスク外差分ゼロを検証する。

## 作業置き場(experiments/)

`experiments/` はローカル一時領域で、正本ではなくコミットしない。1件ごとに生成・合成して切り出した透過 WebP を `assets/anomaly-overlays/` に置き、台帳(`prompts/anomalies.yaml`)に登録してコミットしたら、その件の作業フォルダ(`experiments/<件名>/` 配下すべて)を即削除する。生成元・マスク・比較画像・blink 等の作業物は溜めない。

## 差分アセット管理

ゲーム用の正本は共通 baseline と、変化領域を不定形の透過マスクで切り抜いた差分画像。差分を透過範囲に合わせて矩形にトリミングし、元画像内の左上座標と元画像・差分の寸法を記録する。全画面の合成画像は検証用であり量産配布しない。lossless WebP 等の透過形式を使い、元画像に記録座標で重ねた再構成が検証画像と一致することを確認する。生成元、マスク、差分・blink 等の制作資料はゲーム用アセットと分ける。詳細は `assets/anomaly-overlays/README.md`。

看板を架空化する時は、他作品の名前だけでなく実際のロゴやモチーフも参照し、旧店舗の意匠を残さない。同じ店が画面端に一部しか写っていない看板や別カメラにも現れる場合、断片まで同じ架空店に統一する。文字・絵だけが鮮明に浮かないよう、元写真の劣化、色、ぼけ、光、粒子に合わせて局所調整し、原寸で確認する。
元看板の図形レイアウト（例えば橙色の四角と内側の白い丸）は守り、文字と他作品由来の小さなロゴを元の表示面内に収める。ロゴを看板いっぱいに拡大しない。昭和の手描きらしさは細い不均一な筆致と適切なサイズで表し、機械的な書体や過度なぼかしを避ける。

## 追加前の類似チェック

新しい候補の記録や生成に着手する前に、`prompts/anomalies.yaml` の制作済み・試作と `prompts/candidate-pool.md` の未制作案の両方を検索する。対象要素ID、カメラ、物の名前、同義語、異変タイプを使い、同じ画面だけでなく別画面も確認する。完全一致だけでなく、以下の組み合わせが近く、プレイヤーから見た変化が実質同じ案も拾う。

- 対象（同じ物や似た店先・床など）と変化（出現・消失・移動・複製・色・形・反射など）
- 見た目・位置・大きさ・タイミング・報告カテゴリと、何に気付く異変か

候補から制作する場合、その候補自身は重複として数えず、既存の別IDと比較する。近い案を発見したらIDと共通点・差を記録し、単なる言い換えは追加しない。別カメラや別色だけでも、観察対象や発見の仕方に意味のある違いがあれば残してよい。意図的に似せたシリーズは、その意図と違いを記録する。似ているか不確実なときは断定せず候補として記録し、制作前に見比べる。

新しい案には安定ID、カメラ・対象要素ID、変化、報告カテゴリ、制作状態を記録する。制作したら同じ案を候補一覧から移して `anomalies.yaml` に登録し、透過差分画像のパスと配置・サイズ・検証状態を更新する。登録済み試作と候補を二重に数えない。候補IDや内容を変更する場合は既存素材との対応を壊さず、必要なら関連IDを残す。
